# Settings
- Settings destinations resolve through settingsNavigation.ts with legacy query compatibility; the page gate retains admin/preview and invoice-only Master data access, so navigation never grants access.
- Focused editors reuse existing tenant-scoped hooks, mutations and atomic RPCs; query destinations change presentation only, and long work renders in the detail pane rather than a containing modal.- Settings uses read-first glass cards on the green: a settings list card (groups Organization · Team · Operations · Accounting · Lists · Bani, orange dot from useSettingsSummary) beside one page on computer and tablet; on phone the list, then the page with ‹ Settings. Pages: group label + title, page actions (Add/Invite) top-right via PageAction, then SettingsCard blocks from SettingsForm.tsx showing saved values as Row with one Edit per card (Field rows + SaveBar while editing); Choice cards save on tap; lists sit inside cards. No lines inside cards, no summary numbers, no explainer notes. Merged pages via mergedInto: Purchasing & stock (purchasing+stock), How your team works (approvals+team), Books setup (books+opening). Card processors show one card per processor (merchants, fee range); Edit opens the existing editors (?edit=1). Each venue uses tabs Seats · Service periods · Closures · Stock areas · Location · Status. A venue's account mapping lives only in Finance › Accounting › How things post.
- Client Settings only holds what a client runs day to day. Business = Company (read-only for clients, one card) + Venues (mergedInto venues→company; clients change seats, service periods, closures, stock areas and location only). No box inside a box; tables use the same thin row lines as every other Bani table; no warning rows (status shows amber). Lists (People) follow Team/Supplier accounts: one card with the count as heading, Toolbar (filter, search) inside, rows open on tap, "No people yet." when empty.
