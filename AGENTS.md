# Project Architecture Rules

- ThemeProvider enforces fixed light resolution without profile or OS hydration; AppLayout mounts one pointer-inert viewport-fixed atmosphere as the first tenant wrapper child behind the floating sidebar and main content, with tenant-scoped glass tokens (including mobile portals), preserving platform styles and overlay stacking.

- All invoice-scanner product links must use `buildMatchLinkPatch`; this keeps supplier-specific Items Master display/save fields atomic while preserving scanned matching evidence.
- Scanner price updates must write the linked supplier entry first and synchronize canonical item cost fields from that supplier conversion; prices are supplier-specific.- "Your Finance Team" figures come only from `supabase/functions/_shared/financeTeamReview.ts`; the `finance-team` function may use AI to word those facts but must reject output with unknown numbers or finding keys, so reviews stay grounded.
- Finance team review snapshots are written only by the `finance-team` function (service role) and are locked by a trigger once finished; history must never be edited.
- Revenue navigation is mounted once inside AppLayout, with route selection and effective-user page access shared by its sidebar destination and local bar; existing page guards and datasets remain independent.
- KPI navigation is mounted once inside AppLayout; its direct sidebar link uses effective-user page visibility/access and its local tabs use existing KPI capabilities, keeping route guards and secondary page controls independent.
- People navigation is mounted once inside AppLayout on HR routes, with most-specific-path tab selection; its direct sidebar link preserves existing visibility and all HR AdminRoute guards remain independent.
- Purchasing navigation is mounted once inside AppLayout; direct sidebar sections, mobile section bars and local tabs share route families and use usePurchasingNavigationAccess for effective-user access with server-backed preview role lookup, leaving route guards and page content unchanged.
- Purchasing mode is read through usePurchasingMode from tenant-scoped app_config; only ProcurementDashboardTab uses purchasingOverviewRows to bypass the venue picker for central buying, with explicit tenant-scoped reads for both invoices and revenue, so group figures never mix clients or change other pages' scope.
- Purchasing Overview calculations live in purchasingOverview.ts and are shared by the page and centred dialogs; invoice creation time supplies the last-upload date because invoice headers have no uploaded_at field.
- Purchasing budgets live in purchasing_budgets with an append-only purchasing_budget_changes log; budget math is pure in purchasingOverview.ts (no pace comparisons — spend is only ever compared with the budget itself) and the UI is ProcurementDashboardTab + PurchasingBudgetsDialog, so budget rules change in one place.
- Dashboard-only presentation helpers hold invoice-month defaults and trailing chart months; local wrappers style shared cards and the dashboard owns its header and analysis footer, leaving other pages unchanged.
- Voice routing uses the existing reasoning turn and full conversation, and acknowledgements originate only from confirmed tool work; bounded non-confidential session clips share one cancellable media element. Final speech extracts complete prose without a second model request, keeping text independent of audio.
- Voice capture has one mobile microphone owner (MediaRecorder); wall-clock capture deadlines and abortable stage deadlines must remain independent of analyser levels and recorder start events, with an explicit orb send and recoverable notices instead of discarding quiet recordings.
- Composer dictation uses MediaRecorder + bani-stt (never Web Speech) and only fills the editable draft; the orb has a constant ambient grain/swirl but its level-driven scale and glow come solely from real signals (mic analyser, or PCM envelope at the `<audio>` currentTime), and playback must never be routed through WebAudio.
- Floating Bani is tenant-only with one conversation held in FloatingBaniProvider (shared by global and scanner-hosted instances, reset only on user/tenant/preview change) and relocates into the active scanner host; attachments are read-only analysis in chat-assistant `floatingFiles.ts`; unsaved corrections use server-validated whitelists, supplier-scoped candidates and host-rechecked stable draft/line IDs with mutation revisions, never model-side writes or Save/GRN bypasses.
- Floating Bani classifies attachments (sales report / supplier invoice / expense) and has two navigation actions: `open_sales_scanner` (one file, separate sales slot in `scannerHandoff.ts`, consumed by Sales Data's Scan Receipt) and `open_invoice_scanner`: the server validates the venue and emits an action event, the client hands original in-memory File objects through `src/utils/scannerHandoff.ts` (consumed by request id, re-armed only on real scan failure), and the scanner runs its normal parse pipeline; unsaved reviews are never replaced without explicit user consent, and Save/GRN stay on the existing explicit workflow.
- Sales receipt corrections (Scan Receipt's Fix with Bani) go through chat-assistant `salesReview.ts` and `src/utils/salesReceiptCorrections.ts`: field whitelist + tenant venues validated on server and client, applied only on user Apply against the same draft; Save stays manual.
- Bani contextual memory lives in chat-assistant `contextMemory.ts`: past record notes plus `bani_memory_notes` (server-written, venue/supplier scoped) are injected as untrusted background, never as rules; post-scan verdicts come from deterministic scanner checks, not extra model calls.
- Unmatched invoice lines get up to 3 Bani suggestions (`src/utils/baniLineSuggestions.ts`) auto-requested once per draft+supplier, strictly supplier-scoped and never auto-linked; saving invoice code/wording to Items Master happens only on the user's explicit "Save to master" tap.
- Sales receipt scans learn silently: on save, `collectScanLearning` (src/utils/salesScanLearning.ts) diffs reader output vs saved record and `parse-receipt` (op "learn", service role, field whitelist) upserts venue-scoped `ai_learned_rules`; later scans inject them as untrusted background notes. No Accept & Teach prompts.
- The Launchpad (`/`) is the single tenant front door; its drop zone stages files into the shared Floating Bani composer (`useFloatingBaniAttach`) so classification/routing stays in one place. `/assistant` and `/finance-team` remain routable but are not top-level sidebar links.
- Venue filtering is one portal-wide scope (`useVenueScope` in `src/hooks/useVenueScope.tsx`, pure rules in `src/utils/venueScope.ts`) mounted once in AppLayout with the top-bar picker and page reminder; pages must not add their own venue view filters (data-entry venue fields are separate), so every page agrees on which venues are shown.
- Venue seats come only from `venue_seat_history` (via `useSeatHistory` + `src/utils/seatHistory.ts`); every seat-based number uses the count that applied on each day, and `venues.seats` is a trigger-maintained mirror of the latest row, so seat history is never lost.
- Revenue pages share `RevenuePageTop` (title, Period left, actions right); multi-venue target views sum per-venue projection rows (`useScopedProjections`), while saving a target always needs exactly one venue.
- List pages build on the shared kit in `src/components/kit/` (PageTop, QuickFilter, Toolbar, FilterPanel, SortMenu, ListRow, StatusPill, DetailPanel); Sales records rules ("doesn't add up", missing days, unusual-day note prompt) live in `src/utils/salesRecordChecks.ts`, so every page looks and checks the same way.
- Sales record notes (`sales_record_notes`) are the only place day explanations live; the Your team engine reads them and treats Closed early / Weather / Private event / POS problem as explaining a drop.
- DailyRecords uses a fixed-column semantic table with optional user-keyed column preferences; missing runs derive from full scoped sales history and tenant-local dates through salesRecordChecks, keeping period filtering from inventing trading start dates.
- Closed days live in `venue_closures` (single days) and `venue_closure_rules` (every-weekday / ranges), resolved only through `src/utils/venueClosures.ts` (client) and the finance-team loader; `venue_closed_days` is deprecated and only kept in sync, so every check agrees on which days were closed.
- Bani action cards: chat-assistant `propose_action` writes a row to `bani_pending_actions` (service-role only, no client grants) and streams an `action_card` event; FloatingBani renders Confirm/Cancel and calls back with `action_id`+`decision`, where the server re-validates ownership, expiry (30 min), single-use status, and re-checks sales conflicts before executing. Card titles for closed days are computed server-side from the validated venue/dates — never trust the model's title. Closed days are only markable for yesterday or earlier (Asia/Hong_Kong).
- Bani must never infer missing sales days from aggregates: `get_missing_sales_days` (chat-assistant) is the authoritative check (no sales AND no closure, through yesterday). `get_venue_closures` exposes closed days so closed days are never flagged as missing.
- Floating Bani briefing: on first open each day with an empty conversation, FloatingBani sends one hidden briefing turn (per identity+date); the Launchpad (YourTeam) auto-runs the finance-team review once per scope per day when the latest review is stale, and the pg_cron job `finance-team-scheduled-reviews` (hourly at :05) generates the daily review after 7 AM tenant time via `finance_team_schedules`.
