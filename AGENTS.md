# Project Architecture Rules
- Everything is built universal: one path for every client (KHAMBU included). Never add a client-only or new-clients-only path; when an older client works differently, migrate it onto the shared path from a dated start, leaving posted days unchanged.
Read nested AGENTS.md (Finance, People, assistant/voice, Alerts, chat-assistant) before related changes.
- All populated tests use existing Finance isolated QA tenant ff000000-0000-4000-8000-000000000001; remove test rows afterwards. Never create test tenants/users or insert fixtures into real tenants.

- ThemeProvider fixes light mode, no profile/OS hydration. AppLayout has one pointer-inert fixed atmosphere behind sidebar/content; glass tokens cover mobile portals and platform stacking.

- Scanner links use `buildMatchLinkPatch` atomically; display copies never alter evidence, AI, validation or saves.
- Scanner prices write the supplier entry first, then sync canonical costs through its conversion. Finance-team figures come only from `_shared/financeTeamReview.ts`; AI wording rejects unknown numbers or finding keys.
- Isolated matcher owns its model, pre-date context and hard checks; admin backtest writes only match_backtest_results, never scanner or financial data. Mutable master fields use earlier evidence or are omitted; no snapshots.
- Tenant shell owns Outlet/auth redirects; content gates retain page/admin/preview/KPI checks. Cache keys isolate user/tenant/preview; no cross-identity placeholders. Only Revenue/People Overview reuse fresh data; Sales realtime invalidates. Tenant/preview changes remount content, not shell.
- Section nav mounts once; People uses shell phone pills, sidebar desktop and PageTop, no tabs. Purchasing uses server preview roles; Settings uses scoped editors/atomic category RPCs; People reads Approvals.
- usePurchasingMode reads tenant-scoped app_config. Only ProcurementDashboardTab uses purchasingOverviewRows to bypass venue scope for central buying; invoices and revenue remain explicitly tenant-scoped, without changing other pages.
- Purchasing uses purchasingOverview.ts; directoryRows unifies stock/expense profiles via reversible aliases without financial relinks.
- Purchasing budgets use invoker save_purchasing_budgets for atomic RLS budget/history; purchasingOverview.ts owns budget math and full-month per-venue buildProjectionRows forecast aggregation, usePurchasingBudgets loads picked months independently. Suggestions pass unsaved maps to the editor. Budget history replays per venue/category with Hong Kong day boundaries while preserving untouched venue contributions, preventing split history or conflated venues.
- Expenses use account coverage and source-linked accruals; month-end prepares only drafts, with explicit selected owner/admin approval and same-account/month/amount manual-booking guards. Pending funded prepaid lines are release drafts. Bills append coverage/reversals; corrections retain originals. Meter changes use confirmed Bani cards; category/alias fixes have audit Undo.
- Settlement credits require exact tenant clearing mappings; a shared merchant clears each venue by that venue's own recorded card sales for the sale day and card type (settlement_line_allocations), never by guesses or equal shares, and is skipped and logged when nothing was recorded. Settlement evidence is never altered.
- Rota person checks use all tenant shifts while cover remains venue-scoped; combined role grids keep shift-specific venue actions. Server people_week_sent guards whole-week confirmation so venue drafts never imply readiness.
- Finance: owner-only reopening; payments delegate posting. Source links keep originals; invoice date RPCs pair corrections, compensating closed periods in the current open month. Books reads drift; documents keep RLS/People access.
- Floating Bani is tenant-only with one conversation held in FloatingBaniProvider (shared by global and scanner-hosted instances, reset only on user/tenant/preview change) and relocates into the active scanner host; attachments are read-only analysis in chat-assistant `floatingFiles.ts`; unsaved corrections use server-validated whitelists, supplier-scoped candidates and host-rechecked stable draft/line IDs with mutation revisions, never model-side writes or Save/GRN bypasses.
- Floating Bani classifies attachments (sales report / supplier invoice / expense). Expenses use `open_expense_scanner` (kind bill|cash, one file): ChatExpenseScan (admin, not preview) reads bills with the shared billFromScan.ts (readBillFiles + billDraftFromScan, also used by Expenses › Bills) and slips with cashSlip.ts (also used by Petty Cash › Import). Bills show ChatBillCard (category lines with accounts, read-only regular-cost comparison from findRegularCost) and save only through useExpenseBills.saveBill as pending_review (Send for approval, every line needs an account) or draft (Hold) after an in-panel confirm — never approved or posted from chat; unknown suppliers, contracts, statements with balances, unclear venues, unbalanced lines and duplicates go to Expenses › Bills via stageStatementBill. Slips show ChatCashSlipCard and insert pending petty_cash_receipts (insertPendingCashSlip) for a manager. Bank statements and card payout reports use `open_cash_upload` (kind statement|payout): ChatCashUpload (admin, not preview) loads them in the background through Cash's own loaders — loadStatementFile in bankStatementImport.ts (also Cash › Upload) and uploadPayoutFile/parsePayoutImport/savePayoutBatches in payoutImport.ts (also Card payouts), each hand-off runs once per id — and replies one line per file; it asks only which account an unknown statement is, and sends unbalanced statements, unknown merchants or non-KPay reports to Cash. Nothing posts. Sales and invoices have two navigation actions: `open_sales_scanner` (one file, separate sales slot in `scannerHandoff.ts`, consumed by Sales Data's Scan Receipt) and `open_invoice_scanner`: the server validates the venue and emits an action event, the client hands original in-memory File objects through `src/utils/scannerHandoff.ts` (consumed by request id, re-armed only on real scan failure), and the scanner runs its normal parse pipeline; unsaved reviews are never replaced without explicit user consent, and Save/GRN stay on the existing explicit workflow. A single plain invoice is booked in chat instead: ChatInvoiceScan mounts InvoiceScanner variant="chat" (same parse, matching, duplicate/blocking gates) as ChatScanCard — a Rillet-style table where the receiver ticks every line (Tick all allowed), changes received counts with a required reason from the shared receivingReasons.ts list (Other needs a note; differences dispute and hold money), sees Bani's supplier-price check read-only (Was …), can change due date/paid and delivery date, then Book (Approved/Disputed) or Hold for review (Draft) through an in-panel confirm, both running the shared saveScannerInvoice path; anything unclear opens the full review. A single sales receipt is recorded in chat too: ChatSalesScan (Scan Receipt access, not preview) reads it with the shared salesReceiptRead.ts and shows ChatSalesCard as a statement card (printed lines only, Total sales and Total paid; unsure or off figures amber and editable with Scan Receipt rules via applySalesFigure; diagnoseSalesScan must balance and the date be valid before Record). Venue is picked only from active venues when unmatched; deferred revenue, line-by-line clients or zero sales go to the full review. Record opens an in-panel "Record sales?" confirm listing changed figures, whose Record calls the same saveReceiptIntake server intake (a corrected figure must still agree with the independent second read); flags show a short reason and Open review.
- Sales corrections use salesReview.ts + salesReceiptCorrections.ts: whitelisted, tenant-validated, user-applied to the same draft, never financial writes.
- Scan Invoice calls match-invoice-lines once per draft/supplier; sure uses buildMatchLinkPatch with stable-line/unchanged-input guards. Manual choices write tenant-scoped match_feedback. Other pages keep their matcher; save guards stay unchanged.
- Scanned sales receipts auto-record only through parse-receipt `intake.ts` using pure rules in `_shared/receiptAutoPost.ts`: figures must balance, venue/date valid, no existing same-venue-day sales or closure, and an independent second model read must agree field-by-field; insert/journal run as the user; otherwise a non-posting intake with reasons.
- One Bani typing box per screen: on `/` FloatingBani renders its composer as the page bar and the conversation inline (Landing hides cards while open); elsewhere it is the 44px sphere toggling a non-blocking window anchored above it. Landing pop-ups never contain composers.
- `/` is Landing (reuses `src/lib/financeTeamRoles.ts` roleViews + landingNumbers.ts, only opens pop-ups/links); `/assistant`, `/finance-team`, `/your-team`, `/kpis/*` redirect to `/`. Sidebar counts use useTeamOpenCounts (same review cache key as Landing).
- Venue filtering is one portal-wide scope (`useVenueScope` in `src/hooks/useVenueScope.tsx`, pure rules in `src/utils/venueScope.ts`) mounted once in AppLayout with the top-bar picker and page reminder; pages must not add their own venue view filters (data-entry venue fields are separate), so every page agrees on which venues are shown.
- Business setup is Bani-only: organizations writes and venue insert/delete need is_platform_admin; venue name/is_active/is_system/tenant/company changes are blocked for others by trigger venues_setup_fields_bani_only (service role allowed). Businesses keep operational venue fields (seats, notes, location). Settings shows company and venues read-only to non-platform admins. The control plane client page (ClientDetail) edits company and venues, shows read-only setup from src/utils/clientSetup.ts (no manual checklist) and sets tenants.users_managed_by (default 'bani'): while 'bani', only platform/super admins change a client's users (RLS via client_manages_users + create-user, which also whitelists roles); Settings › Users is read-only for the client. has_role() is global: every write policy using it must also check user_has_tenant(auth.uid(), tenant_id). SECURITY DEFINER functions taking a tenant must check membership (user_has_tenant/is_platform_admin) or be revoked from anon/authenticated when only called by other definer functions or the server.
- Seats use dated venue_seat_history via useSeatHistory/seatHistory.ts; venues.seats is only the trigger-maintained latest mirror.
- Tables and charts follow src/styles/tables.css + kit/chartSize.ts portal-wide: money/numbers/dates/statuses never wrap or truncate (tables scroll sideways, column 1 frozen on phone); only name columns truncate on one line at --bani-name-max (220px computer / 140px phone) with the full name in title and on row tap; 13px text, 12px headings, 44px rows; every chart uses chartHeight() (170px phone / 240px computer), sparklines excepted. Never set per-page table or chart sizes.
- Every screen enters through AppLayout's PageStage (PageMotion.tsx, keyed by path + ?tab/?view): held clear until first loads settle (max 2.5s), then cards rise and contents sharpen from blur; RevenueEnter/Num wait for usePageRevealed. Cards are found by .card-glass/.glass-surface/[data-card]/[data-rv]; never re-add a per-page route fade.
- Revenue/Purchasing/Stock share SectionPillRow/portaled tabs; Register/GRNs reuse Invoices; dates use PeriodControl/usePagePeriod with books windows and explicit future plans. purchaseRegister owns item math; stockPresentation owns On hand. StockCountScreen/useStockCount uses save_stock_count_area for locked totals/unknowns; stockCountReview owns gaps; read-stock-count reuses MATCHER_MODEL and validated candidates. Sent counts are immutable with whole-count approval; browser speech is stock-only. Downloads filtered; Documents redirects.
- Lists use kit; salesRecordChecks owns Sales checks; menuCosts owns RLS-refreshed menu math/bought drafts. supplierAccounts/supplierDeposits own lists/received Assets; invoker confirmations/idempotent returns never sync invoices/POs.
- Revenue targets are saved by line in revenue_daily_projections (line_kind day|period|delivery|event, unique per line_key; DB trigger checks venue/period tenant). Lines come only from src/utils/targetLines.ts: a venue's Settings periods (0–1 = one day line, 2+ = one per period, forecast only from period-tagged sales), delivery from Deliveroo/Foodpanda/Keeta history, named events; a buyout is a labelled period line. Editing one line saves the whole venue-day; readers needing one figure per venue-day sum lines (sumProjectionRows / revenuePlan sumLines); Bani whole-day plans skip line-planned days (lineDays).
- Sales notes store drop explanations (Closed early/Weather/Private event/POS problem).
- DailyRecords uses a fixed-column semantic table with optional user-keyed column preferences; missing runs derive from full scoped sales history and tenant-local dates through salesRecordChecks, so period filtering never invents starts.
- Closed days live in `venue_closures` (single days) and `venue_closure_rules` (every-weekday / ranges), resolved only through `src/utils/venueClosures.ts` (client) and the finance-team loader; `venue_closed_days` is deprecated and only kept in sync, so every check agrees on which days were closed.
- Floating Bani uses the permission-scoped read-only inbox; pending lists stay in chat, completion delegates to smart_alert_action. Identity-scoped continuation/file handoffs retain reviewed uploads. Alert followUp rules distinguish uploads from failures, require evidenced deadlines/cost windows, and use admin-validated person routing plus recipient page/venue checks to prevent guessed outages or privilege escalation.
- Invoice review_status: Draft, To approve, Approved, Disputed, Voided (legacy "Under Review" stays readable); scanner saves map via mapScannerReviewStatus (src/utils/invoiceStatus.ts). Drafts are excluded from Purchasing Overview and payables. Disputed invoices hold back invoices.held_amount (per-line max(0, invoiced − accepted)); usePayables outstanding = max(0, total − paid − held). Delivery problems go through DeliveryCheckDialog (problem-only, from invoice or GRN detail): every issue takes an affected quantity, received = current − affected, unaffected lines keep received qty, and saving disputes the GRN + invoice and adds affected × unit price to held_amount (src/utils/deliveryCheck.ts). GRN received_date = invoice date (Hong Kong), unless the receiver confirmed a delivery date in Bani chat. tenant_members.purchasing_role is display-only, admin-edited in User Access.

- Regular-cost approvals use the atomic selected-items RPC; contract strips share the read-only regular plan. Expense documents fetch fresh signed links and validate bytes before rendering so errors never render as documents. Receipt evidence links append comma-separated paths without financial writes.
- Finance draft, source-approval, tax, account merge and report-allocation safeguards live in src/pages/finance/AGENTS.md; read it for related components, hooks and server functions too.
- Restaurant P&L uses a read-only restaurantPL row model for the statement and exports, with explicit posted-payroll reconciliation; this preserves operations totals while exposing account detail.


- Access (in rollout): one role per person per tenant in tenant_roles/tenant_user_access (+venues, exceptions, history); access_level/money_level/can_see_venue/is_owner are the only checks new rules and server functions may use, and they fall back to legacy behaviour until a person's status is active. Bani sets what each of a client's 9 standard roles can do on the control plane (ClientDetail › ClientRoles, save_tenant_role, platform admins only); the client only assigns a role and venues in Settings › People (RoleAssign.tsx, assign_user_role: Bani always, client admins only when users_managed_by='client'; only Bani gives or changes Owner; nobody but Bani changes their own access). Labels/lines live in src/utils/roleAccess.ts (0–3 = No access/See/Do/Approve). Adding a person or resetting a password (create-user, action reset) creates a readable temporary password (TempPasswordCard: copy, WhatsApp, email) kept in user_metadata.temp_password with must_set_password + temp_password_set_at, so managers can Show it again (create-user/bani-team action show) until the person sets their own (SetOwnPassword clears it) or 7 days pass; TenantShell shows SetOwnPassword until they set their own, and refuses temporary passwords older than 7 days (client-side check). Only Bani resets an owner's password. Bani team logins live on the control plane (/platform/team, BaniTeam.tsx, server bani-team): all Bani admins for now, held as platform_admin in the internal tenant slug bani-internal (status internal, hidden from Clients); new logins are stripped of the old triggers' automatic KHAMBU membership (create-user does the same for client staff). PlatformRoute also shows SetOwnPassword.
- Confirmed team notifications persist one recipient-only message per card/person before unchanged push delivery; Floating Bani reads through identity-scoped useBaniTeamMessages and marks read only after displaying it, while job-role targeting never changes access assignments.
- Alert JWTs refresh once for the same user to recover 401s.
- Revenue setup is universal (every client, KHAMBU included): Settings › Revenue setup (RevenueMapping.tsx, rules in src/utils/revenueMapping.ts), edited by Bani or a role with Approve on Finance through save_sales_mapping, which replaces sales_report_lines (aliases = other printed names, method = payment method/delivery platform, processor_ids, gl_account_id or venue_accounts per venue, legacy_field kept for fixed-field scanners) and stores a dated version in sales_mapping_versions. A client already scanning on the standard fields starts from those fields with How things post accounts (prefillDraft). From a version's start date the journal rebuild posts each day with _post_line_mode_sales (sales_day_on_setup decides; earlier days keep the fixed-field posting, posted days never change); payment lines post as payment_settlement_clearing with payment_method so card payouts still match by venue and card type; a day with a line not set up, a line without an account for that venue, or that does not balance is held in sales_posting_holds, never balanced to suspense. Line-by-line days (scanned or typed) fill the standard payment/delivery columns by method. The control plane shows status only (ClientRevenue) and Edit enters the client.
