# Project Architecture Rules
Read nested AGENTS.md (Finance, People, assistant/voice, Alerts, chat-assistant) before related changes.
- All populated tests use existing Finance isolated QA tenant ff000000-0000-4000-8000-000000000001; remove test rows afterwards. Never create test tenants/users or insert fixtures into real tenants.

- ThemeProvider fixes light mode, no profile/OS hydration. AppLayout has one pointer-inert fixed atmosphere behind sidebar/content; glass tokens cover mobile portals and platform stacking.

- Scanner links use `buildMatchLinkPatch` atomically; display copies never alter evidence, AI, validation or saves.
- Scanner prices write the supplier entry first, then sync canonical costs through its conversion. Finance-team figures come only from `_shared/financeTeamReview.ts`; AI wording rejects unknown numbers or finding keys.
- Isolated matcher owns its model, pre-date context and hard checks; admin backtest writes only match_backtest_results, never scanner or financial data. Mutable master fields use earlier evidence or are omitted; no snapshots.
- Tenant shell owns Outlet/auth redirects; content gates retain page/admin/preview/KPI checks. Cache keys isolate user/tenant/preview; no cross-identity placeholders. Only Revenue/People Overview reuse fresh data; Sales realtime invalidates. Tenant/preview changes remount content, not shell.
- Section nav mounts once; People uses shell phone pills, sidebar desktop and PageTop, no tabs. Purchasing uses server preview roles; Settings uses scoped editors/atomic category RPCs; People reads Approvals.
- usePurchasingMode reads tenant-scoped app_config. Only ProcurementDashboardTab uses purchasingOverviewRows to bypass venue scope for central buying; invoices and revenue remain explicitly tenant-scoped, without changing other pages.
- Purchasing uses purchasingOverview.ts; directoryRows unifies stock/expense profiles via reversible aliases without financial relinks.
- Purchasing budgets use invoker save_purchasing_budgets for atomic RLS budget/history; purchasingOverview.ts owns budget math and full-month per-venue buildProjectionRows forecast aggregation, usePurchasingBudgets loads picked months independently. Suggestions pass unsaved maps to the editor. Budget history replays per venue/category with Hong Kong day boundaries while preserving untouched venue contributions, preventing split history or conflated venues.
- Expenses use account coverage and source-linked accruals; month-end prepares only drafts, with explicit selected owner/admin approval and same-account/month/amount manual-booking guards. Pending funded prepaid lines are release drafts. Bills append coverage/reversals; corrections retain originals. Meter changes use confirmed Bani cards; category/alias fixes have audit Undo.
- Settlement credits require explicit batch venues and exact tenant clearing mappings; shared merchants never use generic fallbacks.
- Rota person checks use all tenant shifts while cover remains venue-scoped; combined role grids keep shift-specific venue actions. Server people_week_sent guards whole-week confirmation so venue drafts never imply readiness.
- Finance: owner-only reopening; payments delegate posting. Source links keep originals; invoice date RPCs pair corrections, compensating closed periods in the current open month. Books reads drift; documents keep RLS/People access.
- Floating Bani is tenant-only with one conversation held in FloatingBaniProvider (shared by global and scanner-hosted instances, reset only on user/tenant/preview change) and relocates into the active scanner host; attachments are read-only analysis in chat-assistant `floatingFiles.ts`; unsaved corrections use server-validated whitelists, supplier-scoped candidates and host-rechecked stable draft/line IDs with mutation revisions, never model-side writes or Save/GRN bypasses.
- Floating Bani classifies attachments (sales report / supplier invoice / expense) and has two navigation actions: `open_sales_scanner` (one file, separate sales slot in `scannerHandoff.ts`, consumed by Sales Data's Scan Receipt) and `open_invoice_scanner`: the server validates the venue and emits an action event, the client hands original in-memory File objects through `src/utils/scannerHandoff.ts` (consumed by request id, re-armed only on real scan failure), and the scanner runs its normal parse pipeline; unsaved reviews are never replaced without explicit user consent, and Save/GRN stay on the existing explicit workflow.
- Sales corrections use salesReview.ts + salesReceiptCorrections.ts: whitelisted, tenant-validated, user-applied to the same draft, never financial writes.
- Scan Invoice calls match-invoice-lines once per draft/supplier; sure uses buildMatchLinkPatch with stable-line/unchanged-input guards. Manual choices write tenant-scoped match_feedback. Other pages keep their matcher; save guards stay unchanged.
- Scanned sales receipts auto-record only through parse-receipt `intake.ts` using pure rules in `_shared/receiptAutoPost.ts`: figures must balance, venue/date valid, no existing same-venue-day sales or closure, and an independent second model read must agree field-by-field; insert/journal run as the user; otherwise a non-posting intake with reasons.
- One Bani typing box per screen: on `/` FloatingBani renders its composer as the page bar and the conversation inline (Landing hides cards while open); elsewhere it is the 44px sphere toggling a non-blocking window anchored above it. Landing pop-ups never contain composers.
- `/` is Landing (reuses YourTeam roleViews + landingNumbers.ts, only opens pop-ups/links); `/assistant`, `/finance-team`, `/your-team`, `/kpis/*` redirect to `/`. Sidebar counts use useTeamOpenCounts (same review cache key as Landing).
- Venue filtering is one portal-wide scope (`useVenueScope` in `src/hooks/useVenueScope.tsx`, pure rules in `src/utils/venueScope.ts`) mounted once in AppLayout with the top-bar picker and page reminder; pages must not add their own venue view filters (data-entry venue fields are separate), so every page agrees on which venues are shown.
- Seats use dated venue_seat_history via useSeatHistory/seatHistory.ts; venues.seats is only the trigger-maintained latest mirror.
- Revenue/Purchasing/Stock share SectionPillRow/portaled tabs; Register/GRNs reuse Invoices; dates use PeriodControl/usePagePeriod with books windows and explicit future plans. purchaseRegister owns item math; stockPresentation owns On hand. StockCountScreen/useStockCount uses save_stock_count_area for locked totals/unknowns; stockCountReview owns gaps; read-stock-count reuses MATCHER_MODEL and validated candidates. Sent counts are immutable with whole-count approval; browser speech is stock-only. Downloads filtered; Documents redirects.
- Lists use kit; salesRecordChecks owns Sales checks; menuCosts owns RLS-refreshed menu math/bought drafts. supplierAccounts/supplierDeposits own lists/received Assets; invoker confirmations/idempotent returns never sync invoices/POs.
- Sales notes store drop explanations (Closed early/Weather/Private event/POS problem).
- DailyRecords uses a fixed-column semantic table with optional user-keyed column preferences; missing runs derive from full scoped sales history and tenant-local dates through salesRecordChecks, so period filtering never invents starts.
- Closed days live in `venue_closures` (single days) and `venue_closure_rules` (every-weekday / ranges), resolved only through `src/utils/venueClosures.ts` (client) and the finance-team loader; `venue_closed_days` is deprecated and only kept in sync, so every check agrees on which days were closed.
- Floating Bani uses the permission-scoped read-only inbox; pending lists stay in chat, completion delegates to smart_alert_action. Identity-scoped continuation/file handoffs retain reviewed uploads. Alert followUp rules distinguish uploads from failures, require evidenced deadlines/cost windows, and use admin-validated person routing plus recipient page/venue checks to prevent guessed outages or privilege escalation.
- Invoice review_status: Draft, To approve, Approved, Disputed, Voided (legacy "Under Review" stays readable); scanner saves map via mapScannerReviewStatus (src/utils/invoiceStatus.ts). Drafts are excluded from Purchasing Overview and payables. Disputed invoices hold back invoices.held_amount (per-line max(0, invoiced − accepted)); usePayables outstanding = max(0, total − paid − held). Delivery problems go through DeliveryCheckDialog (problem-only, from invoice or GRN detail): every issue takes an affected quantity, received = current − affected, unaffected lines keep received qty, and saving disputes the GRN + invoice and adds affected × unit price to held_amount (src/utils/deliveryCheck.ts). GRN received_date = invoice date (Hong Kong). tenant_members.purchasing_role is display-only, admin-edited in User Access.

- Regular-cost approvals use the atomic selected-items RPC; contract strips share the read-only regular plan. Expense documents fetch fresh signed links and validate bytes before rendering so errors never render as documents. Receipt evidence links append comma-separated paths without financial writes.
- Finance draft, source-approval, tax, account merge and report-allocation safeguards live in src/pages/finance/AGENTS.md; read it for related components, hooks and server functions too.
- Restaurant P&L uses a read-only restaurantPL row model for the statement and exports, with explicit posted-payroll reconciliation; this preserves operations totals while exposing account detail.


- Access (in rollout): one role per person per tenant in tenant_roles/tenant_user_access (+venues, exceptions, history); access_level/money_level/can_see_venue/is_owner are the only checks new rules and server functions may use, and they fall back to legacy behaviour until a person's status is active.
- Confirmed team notifications persist one recipient-only message per card/person before unchanged push delivery; Floating Bani reads through identity-scoped useBaniTeamMessages and marks read only after displaying it, while job-role targeting never changes access assignments.
- Alert JWTs refresh once for the same user to recover 401s.
- Home tiles use landingAccrual.ts (display-only accrual: pro-rated last payroll month, menu-recipe theoretical stock + logged waste, pro-rated running costs) so open months never show zero costs; booked figures win once posted.
